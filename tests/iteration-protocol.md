# 迭代协议

只在维护者明确说明「正在做测试复盘，要修改这个 Skill」时使用。普通用户的使用反馈不触发本协议。

## 一、一次迭代只解决一类问题

收到反馈后，先归类，再动手。一次只改一类，改完立刻回归。

| 问题类型 | 典型表现 | 改哪里 |
|---|---|---|
| 流程问题 | 跳阶段、问太多、不给结论 | `SKILL.md` 的三问主线与「可以开工了」的判定条件 |
| 判断问题 | 主题选错、目标写空、素材不足仍出方案 | 对应的 `references/*.md` 判断规则 |
| 表达问题 | 说教、术语多、复述用户的话 | `SKILL.md` 运行时规则第 2、4 条 |
| 报告问题 | 结构缺组、数据虚构、追加推销 | `references/html-report.md` 与 `assets/report-example.html` |
| 边界问题 | 代写讲稿、给定价、给收入预测 | `references/boundaries.md` |

## 二、把反馈变成可执行规则

反馈通常是一句抱怨，不能直接写进 Skill。先做三步翻译：

1. **找出触发条件**：用户在什么状态下，模型做了什么。
2. **写出可判定的规则**：不用「更温和一些」，用「先复述用户刚说的一个具体细节，再提问」。
3. **补一条禁止行为**：反过来写清什么算失败，否则规则会被绕过。

示例：

> 反馈：「它一上来就让我列大纲，可我连讲什么都还没想清楚。」

- 触发条件：用户只说了「想做课」，没说主题。
- 规则：第 1 问没答完（还没有一句具体的「谁问过你什么」）之前，不进入写法层面的输出。
- 禁止行为：三问未确认前，给出课程大纲、章节标题或幻灯片页纲。

## 三、改 Skill 文本的三条纪律

1. **不写形容词，写动作。** 「更专业」不可执行；「每轮只问一个主问题」可执行。
2. **规则要能被测试。** 每条新规则至少对应 `test-cases.md` 里一个案例，否则下次回归覆盖不到。
3. **不加新阶段。** 三个问题 + 课程包四件是稳定结构。想覆盖更多情况时，改现有环节的判定条件和兜底话术，不要再加一轮提问——用户是来拿课的，不是来填问卷的。

## 四、改动后的回归顺序

1. 跑 `bash scripts/verify-release.sh`，确认结构与防回退标记完整；
2. 逐条过 `tests/regression-checklist.md`；
3. 至少跑 `test-cases.md` 中与本次改动相关的三个案例；
4. 检查报告模板：结构、品牌名、窄屏表现、示例数据是否已替换。

## 五、版本与说明

- 每次发布由自动流程打版本号并生成 Release，不需要手改 `VERSION.md`；
- 提交信息写清「改了什么 + 为什么」，它会直接进入 Release 说明，用户看得到；
- 破坏性改动（改三问主线、改报告四组结构）在提交信息中明确标注，便于老用户知道要重新安装。

## 六、不接受的改动

- 为了「更全面」而增加课程推荐、社群入口、付费承接；
- 把案例替换成通用行业知识，削弱「只用真实经历」的约束；
- 放宽素材门槛，让没有实践的用户也能拿到一份方案单。
